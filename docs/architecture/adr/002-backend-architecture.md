# ADR 002: 백엔드를 기능별로 나누고 엔드포인트에서 요청을 처리한다

- 상태: 승인
- 결정일: 2026-09-30

## 맥락

프로젝트를 시작할 때 사용자·인증, 게시글, 댓글 코드를 어떻게 나누고 비즈니스 로직을 어디에 둘지 정해야 했다. 이 프로젝트는 하나의 FastAPI 애플리케이션과 PostgreSQL로 RealWorld API를 구현한다. 요청이 권한 확인을 거쳐 데이터를 읽거나 저장하고 응답을 만드는 과정을 이해하는 것도 목표였다.

## 대안

### 코드 구성

- **계층별 패키징(Package by Layer):** 라우터, 서비스, 데이터 접근 코드처럼 역할에 따라 파일을 모은다. 한 기능의 처리 과정을 보려면 여러 패키지를 오가야 한다.
- **기능별 패키징(Package by Feature):** 사용자·인증, 게시글, 댓글처럼 기능에 따라 파일을 모은다. 관련 코드를 찾기 쉽지만, 폴더를 나누는 것만으로 모듈 간 의존성이 통제되지는 않는다. [구성 방식 참고](https://simonbrown.je/modular-monolith/)
- **유스케이스별 구성(Vertical Slice):** 회원가입이나 게시글 생성처럼 작업별로 코드를 모은다. 개별 작업을 따라가기 쉽지만, 여러 작업이 공유하는 코드를 관리해야 한다.
- **컴포넌트별 구성(Package by Component):** 기능별 코드를 묶고 다른 모듈에 공개할 인터페이스를 정한다. 의존성을 통제하기 좋지만, 초기부터 모듈 경계를 설계해야 한다.

### 요청 처리

- **엔드포인트에서 처리:** 엔드포인트 함수가 요청의 비즈니스 로직과 DB 작업을 조정한다. 한 요청의 처리 절차를 함수에 담는 [트랜잭션 스크립트(Transaction Script)](https://martinfowler.com/eaaCatalog/transactionScript.html)에 가깝다.
- **서비스 계층(Service Layer) 추가:** 엔드포인트는 HTTP 요청·응답을 다루고, 서비스가 비즈니스 로직과 DB 작업을 맡는다.
- **서비스 계층과 리포지토리(Repository) 추가:** 서비스는 비즈니스 로직을 맡고, 리포지토리는 데이터 조회·저장을 맡는다.

## 결정

백엔드를 사용자·인증, 게시글, 댓글의 기능별 모듈로 나눈다. 각 모듈의 엔드포인트 함수가 요청의 비즈니스 로직과 SQLAlchemy 작업을 조정한다.

입력·응답 모델, 인증, DB 세션 생성은 각자의 모듈에 두고, 여러 곳에서 쓰거나 따로 이해하는 편이 나은 작업은 기능별 헬퍼로 분리한다. 서비스·리포지토리 계층은 처음부터 만들지 않는다.

## 근거

관련 코드를 기능별로 모으면 요청부터 데이터 저장까지의 흐름을 따라가기 쉽다. 프로젝트 초기에는 같은 비즈니스 로직을 실행할 다른 진입점이나, 별도 계층으로 분리해야 할 데이터 접근 책임이 확인되지 않았다. 필요한 책임이 드러나기 전까지는 구조를 단순하게 유지하는 편이 이 프로젝트의 학습 목표에도 맞는다.

## 결과와 한계

요청 처리 과정을 관련 기능의 코드에서 찾을 수 있다. 대신 엔드포인트 함수가 HTTP 처리, 비즈니스 로직, DB 작업에 함께 관여한다. 기능이 복잡해지면 한곳에 변경 이유가 다른 코드가 쌓일 수 있다.

같은 로직이나 쿼리를 여러 엔드포인트에서 사용하면 중복이 생길 수 있다. 기능별로 파일을 나눴어도 인증·게시글·댓글 코드는 서로 참조하므로 모듈이 완전히 독립적인 것은 아니다. DB 작업을 포함한 요청 처리 전체는 DB 없이 작은 단위로 검증하기도 어렵다.

이런 문제가 실제로 나타나면 먼저 기능별 헬퍼로 해결할 수 있는지 살펴본다. 비즈니스 로직을 별도로 조정할 필요가 생기면 서비스 계층을, 데이터 접근을 모아야 할 이유가 생기면 리포지토리를 검토한다.
