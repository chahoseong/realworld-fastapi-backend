# ROADMAP.md

이 문서는 프로젝트의 목표·범위·완료 기준과 현재 진행 계획을 공유한다. 목표·범위·완료 기준은 사용자와 합의했으며, 단계 구성은 현재 정보에 기반한 계획이다.

- 진행 계획은 새로운 정보와 작업 결과에 따라 재검토한다.
- 단계 결과가 후속 계획의 전제를 바꾸면 다음 단계에 앞서 변경과 이유를 제안한다.
- 합의된 목표·범위·필수 제약 및 프로젝트 완료 기준의 변경은 사용자와 논의한다.
- 개별 작업과 상세 구현 방법은 각 단계 착수 시 이슈에서 정의한다.

## 프로젝트 목표(Project Objective)

FastAPI와 PostgreSQL로 RealWorld 백엔드를 구현하며 **Backend Application Engineering의 기본기**를 익힌다. 주어진 API 계약을 구현하고, 대표 요청의 처리 흐름을 이해하며, 데이터·권한·실패 처리에 관한 설계 선택을 설명하고 재현 가능한 오류의 원인을 추적·진단할 수 있다.

## 범위(Scope)

### 포함(In Scope)

- **기능:** RealWorld의 JWT 인증, 사용자·프로필, 게시글·댓글, 태그, 즐겨찾기, 팔로우, 목록 필터·페이지네이션과 피드.
- **학습:** 관계형 데이터 모델링, 데이터 제약·transaction, authentication/authorization, validation/error handling, API·DB 통합 테스트.
- **실행·배포:** 로컬 실행 안내와 최소 배포. Docker 또는 이에 준하는 재현 가능한 환경, PostgreSQL 연결·migration, 실제 URL의 API 검증과 기본 로그 확인을 포함한다.

### 제외(Out of Scope)

- 프런트엔드 신규 구현, 사용자 삭제·댓글 수정 등 명세 밖 추가 기능, 임시 Todo API·별도 학습용 endpoint.
- Kubernetes, autoscaling, SLO, production observability 등 Production 수준의 배포·운영과 고급 성능·동시성 튜닝.

## 완료 기준(Success Criteria)

- **외부 계약:** [`docs/api/CONTRACT.md`](api/CONTRACT.md)에 고정된 공식 OpenAPI와 Hurl suite를 기준으로 필수 계약을 모두 충족한다. Hurl 전체 통과 결과와 요구사항별 확인 근거를 남기며, 테스트 통과만으로 미검증 계약의 충족을 간주하지 않는다. 계약 자료 간 충돌은 임의 해석하지 않고 확인·논의한다.
- **자체 검증:** 중요한 실패 위험을 기준으로 테스트한다. Hurl은 외부 API 계약, pytest integration/API test는 실제 PostgreSQL과 애플리케이션을 포함한 중요 동작·실패 조건, unit test는 독립적으로 검증할 가치가 있는 business rule을 담당한다. Hurl과 같은 검증을 불필요하게 중복하지 않는다. [공식 최소 unit test 1개 요구](https://docs.realworld.show/specifications/backend/tests/)는 충족하되 테스트 개수·coverage 수치를 목표로 삼지 않는다.
- **재현·배포:** README로 새 로컬 환경에서 실행·검증을 재현할 수 있다. 배포 환경에서 migration 적용, 실제 URL의 인증·저장·조회, 데이터 유지와 기본 로그를 확인하고 절차·결과를 남긴다.
- **학습 성취:** 기능 완료와 별도로, 사용자가 ① authentication 포함 흐름 ② authorization이 필요한 변경 흐름 ③ 관계 기반 조회 흐름을 코드·실행 결과에 연결해 설명한다. 재현 가능한 오류의 발생 계층·원인·해결 방법도 추적·설명하며, 근거는 관련 이슈에 남긴다.

## 진행 계획(Phases)

| 단계                            | 목표(Objective)                                                 | 완료 기준(Success Criteria)                                                                                                                                                 | 상태(Status) |
| ------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| 1. 첫 Vertical Slice·저장 기반 | 실제 회원가입 기능으로 API→DB 전체 흐름을 이해한다.            | 빈 DB에서`POST /api/users`의 계약(토큰 응답 포함), 사용자 저장·앱 재시작 후 유지 및 주요 입력·중복 실패를 확인한다. 아래 요청 흐름을 코드와 실행 결과로 설명할 수 있다. | 완료         |
| 2. 사용자·인증                 | 사용자를 식별하고 개인 정보 접근을 보호할 수 있다.              | 로그인·현재 사용자 조회·수정·프로필 조회가 계약을 충족하고, 인증 성공·실패의 검증 근거가 있다.                                                                          | 완료         |
| 3. 게시글·댓글                 | 관계 데이터와 소유권에 따라 콘텐츠를 다룰 수 있다.              | 게시글 CRUD, 댓글 생성·조회·삭제, 태그가 계약을 충족하며 데이터 관계·권한 위반의 중요 실패 위험을 검증한다.                                                              | 진행 중      |
| 4. 관계·목록 조회              | 사용자 관계와 조회 조건에 맞는 콘텐츠를 제공한다.               | 팔로우·즐겨찾기와 해제, 필터·페이지네이션·피드의 결과가 준비된 데이터의 기대값과 일치한다.                                                                               | 예정         |
| 5. 통합·배포 검증              | 백엔드의 계약 충족과 학습 성취를 배포 결과까지 연결해 입증한다. | 전체 계약, 로컬 재현, 최소 배포 및 설계 설명·오류 진단에 대한 프로젝트 완료 기준의 근거가 확보된다.                                                                        | 예정         |

**의존성:** 회원가입 → 사용자·인증 → 콘텐츠 → 관계·조회 → 통합·배포 검증. 피드는 팔로우·게시글에 의존한다. 검증과 설명 근거는 각 단계에서 축적한다. 상태는 `예정`, `진행 중`, `완료`, `보류`로 표시하고 완료 기준 충족 시에만 `완료`로 변경한다.

## 미결정 사항(Open Questions)

- **확정 원칙:** 동기 구현을 기본값으로 하고 async는 구체적 필요가 확인될 때 도입한다. architecture·abstraction은 실제 책임 분리·중복 문제를 근거로 도입한다.
- **배포:** 대상·방식·비용 제약은 배포 준비 전에 결정한다.
