# 객체 수준 인가(Object-Level Authorization)와 소유권 검사

이 노트는 사용자를 알아낸 다음, 그 사용자가 **특정 자원에 특정 작업을 해도 되는지** 판단하는 원리를 설명한다. 토큰의 발급·검증 과정은 [JWT와 사용자 인증](008-json-web-token-and-authentication.md)에서 다루고, 여기서는 자원별 권한 판단에 집중한다. 게시글·댓글은 원리를 살펴보기 위한 예시다.

## 인증과 인가는 어떤 질문에 답하는가

**인증(Authentication)**은 “이 요청을 보낸 사용자는 누구인가?”에 답한다. **인가(Authorization)**는 “그 사용자가 요청한 작업을 이 자원에 수행해도 되는가?”에 답한다.

```text
요청 → 사용자 식별 → 대상 자원 확인 → 작업 권한 판단 → 허용 또는 거부
```

유효한 로그인 토큰은 사용자를 식별할 근거이지 모든 자원에 대한 허가증이 아니다. 로그인한 사용자가 자신의 글을 수정할 수 있어도 다른 사용자의 글을 수정할 수 있다는 뜻은 아니다. 반대로 공개 글을 읽는 작업에는 로그인이 필요하지 않을 수도 있다. **같은 자원이라도 행동에 따라 허용 조건이 달라진다.**

## 인가 판단을 이루는 사용자·자원·행동·맥락

인가 규칙(Authorization Policy)은 보통 다음 요소를 함께 고려한다.

| 요소 | 의미 | 질문 예시 |
| --- | --- | --- |
| 요청 주체(Subject) | 작업을 요청한 사용자 또는 시스템 | 누가 요청했는가? |
| 자원(Resource) | 조회·변경하려는 대상 | 어느 글 또는 댓글인가? |
| 행동(Action) | 자원에 하려는 일 | 읽기, 작성, 수정, 삭제 중 무엇인가? |
| 맥락(Context) | 판단에 필요한 관계·상태·환경 | 작성자인가, 같은 조직에 속하는가, 자원이 공개됐는가? |

예를 들어 `사용자 A는 글 X를 읽을 수 있다`와 `사용자 A는 글 X를 삭제할 수 있다`는 다른 규칙이다. 단순히 “로그인한 사용자는 글 API를 사용할 수 있다”라고 정하면 자원과 행동의 차이를 잃는다. 권한은 필요한 작업에만 주는 **최소 권한(Least Privilege)**을 기본으로 하고, 허용 규칙에 맞지 않으면 **기본 거부(Deny by Default)**하는 편이 안전하다. 이는 [OWASP 인가 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)의 기본 원칙이기도 하다.

## 객체 수준 인가와 소유권 규칙

객체 수준 인가는 응용 프로그램 인터페이스(Application Programming Interface, API)의 주소나 함수에 접근할 수 있다는 사실에서 멈추지 않고, **이번 요청이 가리키는 개별 자원**에 대한 권한을 확인한다. 글 수정 API를 사용할 수 있는 사용자라도 모든 글을 수정할 수 있는 것은 아니다.

**소유권(Ownership)**은 이를 판단하는 한 가지 규칙이다. 예를 들어 요청자가 글의 작성자일 때만 글을 수정할 수 있다. 그러나 모든 인가를 작성자 ID 비교로 해결할 수는 없다. 공개 조회, 공동 작업, 관리 권한처럼 다른 허용 근거가 있을 수 있고, 각 행동의 정책은 따로 정해야 한다. [OWASP API 보안 지침](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/)도 API 사용 권한만 확인하고 대상 객체의 권한을 빠뜨리는 문제를 **객체 수준 인가 실패(Broken Object Level Authorization, BOLA)**로 다룬다.

글과 댓글을 예로 들면, 글 작성자와 댓글 작성자는 서로 다른 사람일 수 있다. 글을 삭제할 권한이 있다는 사실만으로 그 글에 달린 **다른 사람의 댓글을 개별 삭제할 권한**이 생기지는 않는다. 글 삭제의 결과로 연결된 댓글이 함께 정리되는 것과 댓글 하나를 직접 삭제하는 권한은 별개의 규칙이다. 삭제 대상이 글인지 댓글인지에 따라 확인할 소유권도 달라진다.

## URL과 자원 ID를 신뢰할 수 없는 이유

웹 주소(Uniform Resource Locator, URL)의 경로나 요청 본문에 있는 자원 식별자(Identifier)는 클라이언트가 바꿀 수 있다. `DELETE /documents/123`을 요청할 수 있다는 사실은 문서 123을 삭제할 권한이 있다는 증거가 아니다. 서버는 식별자로 대상을 찾은 뒤 요청자의 권한을 다시 판단해야 한다. 클라이언트가 소유자 ID를 제출하더라도 그것을 요청자의 신원으로 믿어서는 안 된다.

숫자 ID를 범용 고유 식별자(Universally Unique Identifier, UUID)나 긴 문자열로 바꾸면 추측은 어려워질 수 있다. 그래도 주소가 공유·노출되거나 다른 경로로 알려질 수 있으므로 **식별자를 알아맞히기 어렵다는 사실은 인가를 대신하지 못한다.** 식별자를 바꿔 다른 사람의 자원에 접근할 수 있게 되는 문제를 **안전하지 않은 직접 객체 참조(Insecure Direct Object Reference, IDOR)**라고 부른다. [OWASP의 IDOR 설명](https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html)은 숫자 ID뿐 아니라 UUID·파일 이름·슬러그(slug)도 객체 참조가 될 수 있다고 설명한다.

## 자원 관계를 포함한 인가 판단

하위 자원(Child Resource)의 URL에는 상위 자원(Parent Resource)의 식별자와 하위 자원의 식별자가 함께 있을 수 있다.

```text
DELETE /projects/{project_id}/tasks/{task_id}
```

이때 작업 대상은 `task_id`만으로 정해지지 않는다. 서버는 **그 작업이 URL의 프로젝트에 실제로 속하는지** 확인하고, 그 작업을 요청자가 삭제할 수 있는지도 확인해야 한다.

```text
대상 작업이 존재하는가?
    ↓
그 작업의 project_id가 URL의 project_id와 일치하는가?
    ↓
요청자에게 그 작업을 삭제할 권한이 있는가?
```

관계 확인과 권한 확인은 서로 다르다. 작업이 프로젝트에 속한다는 사실은 **올바른 대상을 찾았다는 조건**이고, 요청자가 삭제할 수 있다는 사실은 **인가 조건**이다. 하나만 확인하면 다른 프로젝트의 작업 ID를 섞어 쓰거나, 올바른 프로젝트 안의 남의 작업을 변경할 여지가 생긴다. 게시글과 댓글도 같은 원리를 보여주는 예시다.

## 거부 응답과 변경 전 검사

하이퍼텍스트 전송 프로토콜(Hypertext Transfer Protocol, HTTP)의 상태 코드(Status Code)는 거부 이유를 구분해 표현할 수 있다. [HTTP 의미를 정의한 RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5)은 유효한 인증 정보가 없는 요청에 `401 Unauthorized`, 이해했지만 수행을 거부하는 요청에 `403 Forbidden`, 대상이 없거나 존재를 알리지 않으려는 경우에 `404 Not Found`를 설명한다. `401`의 영문 이름이 *Unauthorized*여도 보통 **인증 정보가 유효한가**를 먼저 판단하는 응답으로 이해해야 한다. 실제 API의 상태 코드와 오류 본문은 해당 API 계약에 맞춰 정한다.

변경 요청에서는 대상을 찾고 인가를 판단한 뒤에 저장 상태를 바꿔야 한다. 타인의 글 삭제가 거부됐다면 오류 응답만 맞는 것으로 충분하지 않다. 글과 관련 데이터도 이전 상태로 남아야 한다. 권한 확인 뒤 저장 중 오류가 발생했다면 그 변경은 트랜잭션(Transaction)의 실패 처리로 되돌려야 한다. 두 경우 모두 변경이 남지 않을 수 있지만, **인가 거부로 변경을 시작하지 않은 경우**와 **시작한 변경을 취소한 경우**는 원인이 다르다. 트랜잭션의 기초는 [데이터베이스 Engine과 Session](003-database-engine-and-session.md)에서 다룬다.

## 데이터베이스 제약과 인가의 책임 구분

외래 키(Foreign Key, FK)는 댓글이 존재하는 글을 참조하도록 하고, 고유 제약(Unique Constraint)은 특정 값의 중복을 막는다. 이 제약만으로는 **현재 요청자가 그 댓글을 지워도 되는지** 알 수 없다. 데이터의 관계가 유효한지와 사용자의 행동이 허용되는지는 다른 질문이다.

```text
데이터베이스 관계: 이 댓글은 실제 글에 속하는가?
인가 규칙: 이 요청자는 이 댓글을 삭제할 수 있는가?
```

일반적인 외래 키·고유 제약은 누가 HTTP 요청을 보냈는지 고려하지 않는다. 인가 판단은 요청자의 신원과 현재 자원 상태를 아는 계층에서 수행해야 한다. 어떤 계층이 수행하든 관계 제약과 인가 규칙 **둘 다** 충족되어야 한다. 관계형 제약의 원리는 [관계형 데이터 모델링과 참조 무결성](009-relational-data-modeling-and-referential-integrity.md)에서 다룬다.

## 인가 규칙을 설계·검증할 때 확인할 질문

1. 이 행동을 하려면 인증이 필요한가? 공개 조회라면 익명 요청은 어디까지 허용되는가?
2. 요청 주체와 대상 자원을 서버가 각각 어떤 근거로 식별하는가?
3. 허용 조건은 소유권인가, 공유 권한인가, 다른 관계나 상태인가?
4. URL에 상위·하위 자원이 함께 있다면 실제 소속 관계를 확인하는가?
5. 같은 자원에 대한 읽기·수정·삭제가 서로 다른 권한을 필요로 하는가?
6. 허용 규칙에 맞지 않을 때 어떤 응답을 주고, 변경 전후 데이터는 어떤 상태여야 하는가?

검증할 때는 서로 다른 권한을 가진 두 사용자와 자원 두 개를 준비하면 판단을 관찰하기 쉽다. **허용되어야 할 요청**과 **거부되어야 할 요청**을 각각 실행하고, 거부 후에는 자원을 다시 조회해 상태가 유지됐는지 확인한다. ID가 있는 요청은 다른 사용자의 ID와 다른 상위 자원의 ID를 넣은 경우도 살펴본다. 이는 함수마다 테스트를 하나씩 만드는 방식이 아니라, 정책에서 중요한 경계를 확인하는 방식이다.

## 기억할 내용

- 인증은 요청자를 식별하고, 인가는 그 요청자의 특정 자원·행동에 대한 권한을 판단한다.
- 유효한 토큰, 접근 가능한 API, 알기 어려운 자원 ID 중 어느 것도 그 자원에 대한 권한을 증명하지 않는다.
- 소유권은 객체 수준 인가의 한 규칙이다. 공개 조회나 공동 작업에는 다른 허용 조건이 필요할 수 있다.
- 상위·하위 자원의 소속 관계와 요청자의 작업 권한은 각각 확인해야 한다.
- 거부된 변경은 데이터에 남지 않아야 하며, 저장 중 실패를 되돌리는 것과 인가 거부는 구별해야 한다.
- 외래 키는 참조를 지키지만, 요청자의 자원별 권한을 대신 판단하지 않는다.
