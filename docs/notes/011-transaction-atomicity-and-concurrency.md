# 트랜잭션의 원자성과 동시성(Transaction Atomicity and Concurrency)

이 노트는 여러 데이터 변경을 하나의 작업으로 확정하는 방법과, 그 작업을 여러 요청이 동시에 수행할 때 생기는 문제를 설명한다. 특정 API의 처리 순서보다 **무엇을 함께 확정해야 하는지**, **동시에 실행해도 어떤 조건이 지켜져야 하는지**를 판단하는 데 집중한다. 세션(Session)의 기본 사용법은 [데이터베이스 엔진과 세션](003-database-engine-and-session.md), 데이터 관계와 제약은 [관계형 데이터 모델링과 참조 무결성](009-relational-data-modeling-and-referential-integrity.md)에서 다룬다.

## 하나의 작업을 트랜잭션으로 묶는 이유

트랜잭션(Transaction)은 여러 데이터베이스 작업을 하나의 확정 또는 취소 단위로 묶는다. 예를 들어 계좌 A에서 1만 원을 빼고 계좌 B에 1만 원을 더하는 이체에서는 두 변경이 함께 성공해야 한다. 출금만 저장되면 업무 규칙이 깨진다.

트랜잭션의 범위는 SQL 문장 수나 함수 수로 정하지 않는다. **작업이 끝났다고 말하기 위해 함께 성립해야 하는 조건**, 즉 불변식(Invariant)을 기준으로 정한다. 글을 삭제할 때 글과 연결된 데이터의 정리가 함께 완료돼야 한다면, 이를 서로 독립적으로 확정해서는 안 된다. 반대로 긴 외부 통신까지 트랜잭션에 넣으면 잠금(Lock)이나 데이터베이스 자원을 오래 점유할 수 있으므로, 필요한 변경의 경계를 분명히 해야 한다.

## 원자성: 전부 확정하거나 전부 취소하기

원자성(Atomicity)은 하나의 트랜잭션에 속한 변경을 **모두 확정하거나 모두 취소**한다는 성질이다. 이체의 두 변경 중 두 번째가 실패하면 첫 번째 변경도 롤백(Rollback)해 이체 전 상태로 돌린다. 모든 변경이 성공하면 커밋(Commit)으로 함께 확정한다. [PostgreSQL의 트랜잭션 설명](https://www.postgresql.org/docs/18/tutorial-transactions.html)도 이 단위를 여러 단계에 걸친 하나의 작업으로 설명한다.

원자성은 **한 트랜잭션 내부의 부분 반영**을 막는다. 그러나 두 트랜잭션이 같은 데이터를 동시에 읽고 결정할 때 업무 규칙까지 자동으로 지켜 주지는 않는다. 각 요청이 자기 변경을 전부 커밋했어도 두 요청의 최종 결과는 잘못될 수 있다. 이 차이가 원자성과 동시성(Concurrency)을 따로 생각해야 하는 이유다.

## `flush`·`commit`·`rollback`과 변경의 확정 시점

SQLAlchemy 세션을 예로 들면, 플러시(Flush)는 대기 중인 변경을 현재 트랜잭션 안에서 데이터베이스로 보낸다. 이때 SQL이 실행되어 제약 위반이 드러나거나, 같은 트랜잭션이 생성된 값을 다시 읽을 수 있다. **플러시가 성공했다고 변경이 확정된 것은 아니다.**

| 동작 | 의미 | 실패 시 판단에 필요한 점 |
| --- | --- | --- |
| `flush` | 현재 트랜잭션에서 SQL을 실행한다. | 뒤에서 실패하면 아직 확정되지 않은 변경을 롤백할 수 있다. |
| `commit` | 트랜잭션의 변경을 확정한다. | 성공한 뒤에는 그 트랜잭션을 롤백해 되돌릴 수 없다. |
| `rollback` | 현재 트랜잭션의 미확정 변경을 취소한다. | 이미 성공적으로 커밋된 이전 트랜잭션에는 영향을 주지 않는다. |

따라서 실패 후 상태를 확인할 때는 응답 내용이나 같은 세션의 객체 값만 보지 말고, **별도의 세션에서 최종 저장 상태**를 읽는 편이 분명하다. 오류 응답의 상태 코드는 애플리케이션이 예외를 어떻게 처리하는지에 따라 달라지며, 원자성 자체가 특정 HTTP 상태 코드를 정하지는 않는다.

## 격리와 가시성: 다른 트랜잭션에는 무엇이 보이는가

격리(Isolation)는 동시에 실행되는 트랜잭션이 서로의 변경을 어떻게 관찰하는지에 관한 성질이다. 가시성(Visibility)은 특정 시점의 읽기에서 어떤 변경을 볼 수 있는지를 뜻한다. 격리 수준(Isolation Level)에 따라 읽기의 기준과 허용되는 현상이 달라진다.

PostgreSQL의 기본 **읽기 확정(Read Committed)** 수준에서는 일반 `SELECT`가 그 **문장이 시작되기 전에 커밋된 데이터**를 본다. 같은 트랜잭션이 앞서 쓴 값은 스스로 볼 수 있지만, 다른 트랜잭션의 미확정 변경은 보지 못한다. 같은 트랜잭션에서 `SELECT`를 두 번 실행하는 사이 다른 요청이 커밋하면 두 결과가 달라질 수도 있다. 이는 [PostgreSQL의 격리 수준 설명](https://www.postgresql.org/docs/18/transaction-iso.html)에 따른 동작이다.

더 강한 **직렬화 가능(Serializable)** 수준은 성공적으로 커밋된 트랜잭션들의 결과가 어떤 순차 실행과 같도록 제한한다. 충돌을 해결하기 위해 트랜잭션 하나를 실패시킬 수 있으므로 애플리케이션은 필요한 경우 전체 작업을 다시 시도해야 한다. 격리 수준을 올리는 것만으로 모든 요청이 반드시 성공하게 되는 것은 아니다.

## 동시 요청이 만드는 경쟁 조건

경쟁 조건(Race Condition)은 여러 요청의 실행 순서에 따라 결과가 달라지는 상황이다. 남은 좌석이 하나라고 가정하자.

| 시점 | 요청 A | 요청 B |
| --- | --- | --- |
| 1 | 남은 좌석 `1`을 읽음 | |
| 2 | | 남은 좌석 `1`을 읽음 |
| 3 | 예약 한 건을 만들고 남은 좌석을 `0`으로 저장 | |
| 4 | | 예약 한 건을 만들고 남은 좌석을 `0`으로 저장 |

적절한 동시성 제어가 없다면 두 예약은 각각 원자적으로 커밋되어도, 좌석 하나에 예약이 두 건 생길 수 있다. 두 요청 모두 **읽었을 당시에는** 예약 가능하다고 판단했기 때문이다. “먼저 조회해서 가능하면 저장한다”는 애플리케이션 검사만으로는, 조회와 저장 사이에 다른 요청이 끼어드는 일을 막지 못한다.

고유한 이름을 만들 때도 “같은 이름이 없는지 먼저 조회한다”는 검사에 두 요청이 동시에 통과할 수 있다. 동시성 문제를 다룰 때는 **읽은 조건과 저장할 변경 사이를 무엇으로 보호할지** 정해야 한다.

## 잠금·데이터베이스 제약·재시도의 역할

한 가지 수단으로 모든 경쟁 조건을 해결하지는 못한다. 지키려는 조건에 맞춰 다음 수단을 선택한다.

| 수단 | 지키는 방식 | 주의할 점 |
| --- | --- | --- |
| 행 잠금(Row Lock), 예: `SELECT ... FOR UPDATE` | 기존 행을 기준으로 판단하는 요청들이 차례로 그 행을 다루게 한다. | 대기나 교착 상태(Deadlock)가 생길 수 있다. 아직 없는 행 자체는 잠글 수 없다. |
| 고유 제약(Unique Constraint) | 중복되어서는 안 되는 값의 동시 삽입을 데이터베이스가 막는다. | 사전 조회를 대신하는 최종 제약이며, 충돌한 요청의 오류 처리 또는 재시도를 정해야 한다. |
| 조건부 변경(Conditional Update) | 예를 들어 `남은 수량 > 0`일 때만 수량을 줄이고, 실제 변경된 행이 있는지 확인한다. | 조건과 변경을 하나의 데이터베이스 작업으로 표현할 수 있어야 한다. |
| 재시도(Retry) | 충돌로 실패한 **전체 트랜잭션**을 최신 상태를 읽는 단계부터 다시 실행한다. | 재시도할 오류를 구분하고 횟수를 제한해야 한다. 외부 부작용의 중복도 고려해야 한다. |

PostgreSQL에서 `FOR UPDATE`로 잡은 행 잠금은 트랜잭션이 끝날 때까지 유지된다. [명시적 잠금 문서](https://www.postgresql.org/docs/18/explicit-locking.html)는 잠금 대기와 교착 상태도 설명한다. [고유 제약](https://www.postgresql.org/docs/18/ddl-constraints.html)은 데이터 자체의 중복을 막으며, [고유성 검사](https://www.postgresql.org/docs/18/index-unique-checks.html)는 다른 트랜잭션의 삽입과 충돌할 때의 처리를 데이터베이스 안에서 수행한다. 애플리케이션의 사전 조회만으로 이 역할을 대신할 수는 없다.

## 원자성과 동시성을 각각 어떻게 검증할 것인가

두 성질은 서로 다른 실패를 찾으므로 검증 방법도 다르다.

| 검증할 계약 | 검증 방법 | 결과에서 확인할 것 |
| --- | --- | --- |
| 실패 시 부분 반영이 없다. | 여러 변경 중 일부 SQL이 실행된 **뒤, 커밋 전**에 오류를 일으킨다. 이후 별도 세션으로 다시 조회한다. | 관련 데이터가 모두 요청 전 상태이거나 모두 확정된 상태여야 한다. 실패 시에는 일부만 남아 있지 않아야 한다. |
| 특정 경쟁 상황에서도 불변식이 지켜진다. | 실제 데이터베이스 세션 두 개의 실행이 겹치도록 제어한다. | 두 요청의 결과와 최종 저장 상태가 그 상황에서 정한 규칙을 만족해야 한다. |

순차적으로 두 요청을 보내는 테스트는 둘 사이의 겹침을 재현하지 못한다. 반대로 하나의 동시성 테스트가 **모든** 실행 순서를 증명하지도 않는다. 어떤 경쟁 상황과 최종 조건을 검증했는지 명시해야 한다. 테스트용 데이터베이스를 분리하고 상태를 정리하는 방법은 [pytest fixture와 FastAPI 테스트 환경](007-pytest-fixtures-and-fastapi-test-environment.md)을 참고할 수 있다.

## 설계할 때 확인할 질문과 기억할 내용

- 어떤 데이터가 **함께** 바뀌어야 작업이 완료되는가? 그 변경들은 같은 트랜잭션에 있는가?
- 오류가 플러시 뒤나 커밋 직전에 발생해도 부분 데이터가 남지 않는가?
- 동시에 실행되는 요청들이 같은 값이나 관계를 읽고 결정하는가? 그 사이에 값이 바뀌면 어떤 불변식이 깨지는가?
- 그 불변식을 잠금, 제약, 조건부 변경, 격리 수준 중 무엇으로 지킬 것인가? 충돌한 요청은 어떤 결과를 받는가?
- 검증은 응답만 확인하는가, 아니면 별도 세션에서 최종 데이터 상태도 확인하는가?

**기억할 내용:** 원자성은 한 트랜잭션의 변경을 전부 확정하거나 취소한다. 동시성 제어는 여러 트랜잭션이 겹쳐도 정한 불변식을 지키게 한다. 전자를 검증했다고 후자까지 보장되는 것은 아니다.
