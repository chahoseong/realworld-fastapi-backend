# 계약 중심 테스트 설계(Contract-Based Test Design)

이 노트는 **어떤 동작을 왜 검증해야 하는지** 판단하는 기준을 정리한다. 여기서 계약(Contract)은 정해진 조건에서 기능이 보장해야 하는 결과와 상태 변화를 뜻한다. 테스트 환경을 구성하는 방법은 [pytest Fixture와 FastAPI 테스트 환경](007-pytest-fixtures-and-fastapi-test-environment.md)을 참고하고, 이 노트에서는 검증 대상과 시나리오를 선택하는 원리에 집중한다.

## 테스트에서 말하는 계약이란 무엇인가

계약은 “이 함수를 실행한다”보다 구체적이어야 한다. **어떤 조건에서 어떤 행동을 하면 무엇이 일어나야 하는가**로 표현할 수 있어야 한다. 성공 결과뿐 아니라 거부하거나 실패했을 때 유지되어야 하는 상태도 포함한다.

예를 들어 문서 관리 기능의 계약을 다음처럼 정할 수 있다.

- 소유자는 문서 내용을 수정할 수 있으며, 이후 조회에서도 수정한 내용이 보인다.
- 소유자가 아닌 사용자의 삭제 요청은 거부되며, 문서는 그대로 남는다.
- 삭제 작업 중 저장이 실패하면 문서와 그 관계 데이터는 요청 전 상태를 유지한다.

계약의 근거는 요구사항, 업무 규칙, 공개 인터페이스(Public Interface) 명세 등에서 찾는다. 현재 코드가 반환하는 값을 그대로 기대값으로 옮기면 코드의 오류까지 테스트에 복사할 수 있다. 기대 결과가 불명확하다면 먼저 기능이 무엇을 보장해야 하는지 정해야 한다.

하나의 공개 메서드(Public Method)는 정상 처리, 권한 거부, 저장 실패처럼 여러 동작을 가질 수 있다. 반대로 하나의 계약은 여러 함수를 거쳐 구현될 수 있다. 따라서 함수와 테스트를 일대일로 맞추기보다 검증할 동작을 기준으로 나눈다. [Google의 동작 중심 테스트 설명](https://testing.googleblog.com/2014/04/testing-on-toilet-test-behaviors-not.html)도 메서드 경계와 동작 경계가 다를 수 있음을 설명한다.

## 구현보다 관찰 가능한 동작을 검증하기

관찰 가능한 동작(Observable Behavior)은 **선택한 검증 경계 밖에서 확인할 수 있는 결과**다. 단위 테스트에서는 반환값이나 공개 상태일 수 있고, API 테스트에서는 응답이나 이후 조회 결과일 수 있다.

| 검증하려는 계약 | 결과를 확인하는 방법 | 결과만으로 알 수 없는 것 |
| --- | --- | --- |
| 비소유자의 삭제를 거부한다. | 거부 결과와 삭제 대상의 유지 여부를 확인한다. | 거부 응답만 보면 실제로 데이터가 삭제됐는지 알 수 없다. |
| 변경한 내용이 저장된다. | 수정 후 다시 조회해 내용을 확인한다. | 수정 응답에만 변경 값을 넣고 저장하지 않는 오류는 재조회 없이 놓칠 수 있다. |
| 저장 실패 시 부분 반영이 없다. | 실패 후 관련 데이터의 최종 저장 상태를 확인한다. | 예외가 발생했다는 사실만으로 롤백이 성공했는지 알 수 없다. |

`rollback()`이 호출됐다는 검증과 변경이 실제로 취소됐다는 검증은 다르다. 데이터베이스 상태의 복원이 계약이라면 최종 상태를 확인해야 한다. 트랜잭션(Transaction)의 검증은 [원자성과 동시성](011-transaction-atomicity-and-concurrency.md)에서 더 자세히 다룬다.

내부 도우미 함수의 호출 순서나 횟수를 고정하면, 결과가 같은 리팩터링(Refactoring)에도 테스트가 깨질 수 있다. [Google의 변경 감지 테스트 설명](https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html)은 올바른 동작 대신 현재 구현을 복사하는 테스트의 문제를 다룬다.

호출 자체가 계약일 때는 상호작용 검증(Interaction Verification)이 필요할 수 있다. 예를 들어 “승인된 주문에 대해 외부 결제 요청을 한 번만 보낸다”는 규칙에서는 외부 서비스 경계의 요청 횟수와 내용이 검증 대상이다. 다만 모의 객체(Mock)에서 한 번 호출됐다는 결과는 테스트한 경계의 동작을 보여줄 뿐, 실제 외부 서비스에서도 결제가 한 번만 처리됐음을 증명하지는 않는다.

## 단위·통합·API 테스트의 검증 경계

검증 경계(Test Boundary)는 테스트가 어디에서 입력을 주고 결과를 확인하며, 어떤 의존성을 실제로 포함하는지 정한다. 분류 이름만으로 보장 범위를 판단하지 말고 실행 구성을 함께 봐야 한다.

| 종류 | 검증하는 범위 | 발견하기 어려운 오류 |
| --- | --- | --- |
| 단위 테스트(Unit Test) | 좁은 범위의 규칙을 독립적으로 검증한다. 예: 가격과 할인 조건에 따른 최종 금액 | 실제 데이터베이스 제약, 라우팅, 요청·응답 변환 등 포함하지 않은 경계의 오류 |
| 통합 테스트(Integration Test) | 여러 구성 요소가 실제로 연결될 때의 동작을 검증한다. 예: 서비스와 데이터베이스의 저장·조회 | 대체하거나 생략한 외부 시스템, 서버 실행 환경의 오류 |
| API 테스트(API Test) | API 경계에서 입력을 보내고 응답과 후속 동작을 검증한다. | 내부 저장 상태를 직접 확인하지 않으면 드러나지 않는 오류, 요청하지 않은 시나리오 |

이 분류는 서로 완전히 배타적이지 않다. 실제 데이터베이스를 포함하는 API 테스트는 통합 테스트의 성격도 가진다. 프로세스 안의 테스트 클라이언트와 실행 중인 서버에 보내는 HTTP 요청은 모두 API를 다룰 수 있지만, 서버 시작과 네트워크까지 포함하는지는 다르다.

pytest와 Hurl은 도구 이름이다. pytest로 단위 테스트와 실제 DB를 사용하는 통합 테스트를 모두 작성할 수 있고, Hurl로 HTTP 경계의 계약을 확인할 수 있다. 도구가 다르다는 이유만으로 같은 조건과 결과의 검증을 반복할 필요는 없다. 반대로 같은 기능을 다루더라도 실제 의존성이나 확인하는 상태가 다르면 별도의 가치가 있을 수 있다.

독립적인 계산·판단 규칙은 좁은 경계에서 검증하고, 실제 데이터베이스의 제약이나 롤백은 그 데이터베이스를 포함해 검증한다. 테스트 수를 맞추기 위해 API 호출을 감싼 내부 함수의 모의 호출만 검증해도 새로운 보장이 생기는 것은 아니다.

## 정상·오류·경계 시나리오를 선택하는 방법

먼저 요구사항을 **조건 → 행동 → 예상 결과**로 바꾼다. 이후 중요한 오류를 놓치는 조건이 있는지 확인한다.

| 시나리오 | 선택 기준 | 예시 |
| --- | --- | --- |
| 정상 흐름(Happy Path) | 허용된 사용이 요구한 결과를 만드는가? | 소유자가 수정하면 이후 조회에서 수정 내용이 보인다. |
| 오류 흐름(Error Scenario) | 잘못된 입력이나 처리 실패를 어떻게 다루는가? | 잘못된 수정 값은 거부하고 기존 내용을 유지한다. |
| 경계 조건(Boundary Condition) | 규칙의 경계에서 허용 여부나 결과가 달라지는가? | 허용 길이가 100자라면 100자와 101자를 구분한다. |

빈 목록, 선택 입력의 생략, 여러 대상이 같은 값을 공유하는 상황은 계약에 따라 정상 사용일 수도 있다. 드문 입력이라는 이유만으로 오류나 경계 사례라고 부르지 않는다. 중요한 것은 **어떤 규칙을 확인하며 어떤 오류를 발견할 수 있는가**다.

거부나 실패를 검증할 때는 결과와 함께 유지되어야 하는 상태를 정한다. 권한 없는 수정이라면 거부 결과와 기존 내용의 유지가 함께 중요하다. 외부 오류가 난 뒤 일부 데이터가 저장되면 안 되는 작업이라면 관련 데이터까지 확인해야 한다. 관련 없는 모든 테이블을 매번 확인할 필요는 없다.

파라미터화(Parametrization)는 같은 검증 논리를 여러 조건에 적용할 때 사용한다. 예를 들어 “생성되는 식별자는 서로 다르다”는 계약을 같은 제목 두 개와 서로 다른 제목 두 개에 적용할 수 있다. [pytest의 파라미터화 문서](https://docs.pytest.org/en/stable/how-to/parametrize.html)는 `@pytest.mark.parametrize`로 입력 조합마다 테스트를 실행하는 방법을 설명한다.

조건마다 준비·행동·단언이 크게 달라져 테스트 안에 분기가 많아진다면 별도 시나리오로 나누는 편이 읽기 쉽다. 파라미터 이름과 사례 이름에는 `case1`보다 `duplicate_titles`처럼 조건이 드러나는 표현을 사용한다.

## 테스트 이름과 설명으로 보장할 동작 표현하기

테스트 이름은 실패 보고서를 읽는 사람에게 **무슨 조건에서 어떤 동작이 기대와 달랐는지** 알려줘야 한다. 기능 이름만 적으면 보장하는 결과가 드러나지 않는다.

| 불분명한 이름 | 동작을 드러내는 이름 | 보장하려는 내용 |
| --- | --- | --- |
| `test_delete_document` | `test_non_owner_cannot_delete_document` | 비소유자의 삭제 요청을 거부하고 문서를 유지한다. |
| `test_replace_labels` | `test_label_update_preserves_requested_order` | 변경된 라벨 목록이 요청한 순서를 따른다. |
| `test_rollback_called` | `test_failed_deletion_preserves_document_and_labels` | 삭제 실패 후 문서와 라벨 상태가 유지된다. |

이름에 함수명이나 모든 세부 조건을 담을 필요는 없다. 도메인(Domain)의 행동과 중요한 결과를 우선하고, 세부 보장 범위는 설명 문자열(Docstring)로 보완한다.

```python
def test_failed_deletion_preserves_document_and_labels():
    """문서 삭제 중 변경을 확정하기 전에 실패하면 문서와 라벨 상태는 요청 전과 동일하다."""
    ...
```

이는 이름과 설명의 형태를 보여주는 예시다. “저장 함수를 교체하고 예외를 발생시킨다”는 문장은 실패를 재현하는 방법이다. 설명 문자열에는 **그 실패에서 무엇을 보장하는지** 적고, 재현 방법이 읽기 어렵다면 해당 코드 옆에 주석을 둔다. 설명과 이름의 보장 범위는 실제 단언보다 넓어서는 안 된다.

## AAA 구조와 명확한 단언

AAA는 준비(Arrange)·실행(Act)·검증(Assert)을 구분하는 구조다. [Microsoft의 테스트 지침](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-best-practices#arrange-your-tests)은 이 구분이 의존성, 실행 행동, 기대 결과를 읽기 쉽게 드러낸다고 설명한다.

아래는 “비소유자는 문서를 삭제할 수 없다”는 계약을 확인하는 흐름이다.

```text
# Arrange: 준비
사용자 A가 소유한 문서와, 소유자가 아닌 사용자 B를 준비한다.
문서의 기존 내용을 기록한다.

# Act: 실행
사용자 B가 그 문서를 삭제하도록 요청한다.

# Assert: 검증
삭제가 거부됐는지 확인한다.
문서를 다시 조회해 존재 여부와 기존 내용의 유지 여부를 확인한다.
```

검증 단계에서 재조회하는 것도 실행 코드이지만, 의미상 결과를 관찰하기 위한 검증에 속한다. AAA는 문장의 형태가 아니라 **테스트에서 맡는 역할**을 구분한다.

단언(Assertion)은 예상 결과와 실제 결과를 비교한다. 예상값은 요구한 내용이나 준비한 기존 상태에서 가져온다. 제품 코드와 같은 계산을 그대로 반복해 기대값을 만들면 둘이 같은 오류를 공유할 수 있다.

하나의 테스트에 단언이 여러 개 있어도 괜찮다. 삭제 거부 결과와 문서의 유지 여부는 하나의 권한 계약을 함께 설명한다. 반면 삭제 권한과 목록 정렬처럼 독립적인 동작을 한 테스트에 넣으면 실패 원인을 파악하기 어려워진다. **하나의 테스트를 하나의 단언이 아닌, 이해할 수 있는 하나의 동작으로 묶는다.**

순서가 계약이면 목록의 순서를 비교하고, 순서가 계약이 아니면 우연한 반환 순서에 의존하지 않는다. 관련 없는 응답 필드까지 모두 고정하거나, 상태 유지가 중요한데 상태 코드만 확인하는 식의 과도하거나 부족한 단언도 피한다.

## 검증 중복과 검증 공백을 판단하기

검증 중복(Duplicate Coverage)을 판단할 때는 이름이나 도구보다 다음 항목을 비교한다.

| 비교 항목 | 확인할 질문 |
| --- | --- |
| 조건과 행동 | 같은 사전 상태와 입력으로 같은 작업을 수행하는가? |
| 단언 | 같은 결과만 보는가, 저장 상태나 다른 실패 조건을 추가로 확인하는가? |
| 검증 경계 | 실제 의존성, 서버 실행 환경 등을 추가로 포함하는가? |

예를 들어 HTTP 테스트가 수정 성공 응답과 재조회 결과를 이미 확인한다면, 동일한 조건으로 같은 결과만 확인하는 pytest는 추가 가치가 적을 수 있다. 반면 저장 실패를 재현하고 별도 DB 세션에서 관계 데이터의 복원까지 확인하는 pytest는 다른 계약과 상태를 검증한다. 각 테스트가 발견할 수 있는 오류의 차이를 설명할 수 있어야 한다.

검증 공백(Coverage Gap)은 테스트 수가 적다는 뜻이 아니다. 중요한 요구사항을 위반해도 현재 테스트가 통과하는 상황이다. 새로운 테스트를 추가할 때는 “이 오류가 생기면 기존 테스트는 통과하지만 이 테스트는 실패한다”는 차이를 설명할 수 있어야 한다. 같은 계약을 여러 경계에서 검증하는 것이 필요할 때도 있으나, 그 비용에 맞는 목적이 있어야 한다.

## 테스트를 검토할 때 확인할 질문과 기억할 내용

- 요구사항의 어떤 계약을 검증하는가? 조건·행동·예상 결과가 분명한가?
- 어떤 중요한 오류가 발생하면 이 테스트가 실패하는가?
- 구현 방식이 바뀌어도 계약이 유지되면 통과하는가?
- 정상 결과뿐 아니라 거부·실패 후 유지되어야 하는 상태를 확인하는가?
- 실제 의존성이 필요한 계약을 모의 객체의 호출만으로 판단하고 있지는 않은가?
- 기존 테스트가 같은 조건과 결과를 검증하는가? 추가 검증은 어떤 공백을 채우는가?
- 이름과 설명만으로 보장 범위를 예측할 수 있는가? 단언이 그 범위를 뒷받침하는가?
- 테스트가 필요한 상태를 스스로 준비하고, 정리하여 다른 테스트의 우연한 실행 순서에 의존하지 않는가?

**기억할 내용:** 테스트의 가치는 개수보다 중요한 오류를 발견하는 능력에 있다. 계약에서 예상 결과를 정하고, 그 결과를 관찰할 수 있는 경계를 선택한다. 통과 결과는 실행한 조건과 단언의 근거이며, 검증하지 않은 모든 입력과 환경의 정확성을 증명하지는 않는다.
